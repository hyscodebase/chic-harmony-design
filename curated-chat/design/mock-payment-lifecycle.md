# IntentLock Mock 결제 어댑터: 설계 의도와 검증 범위

이 문서는 2026년 7월 24일 개인 프로젝트 설계 대화의 재사용 가능한 요구사항을 독립적으로 요약하고, 2026년 10월 26일에 읽은 소스와 대조한 기록이다. 대화 원문이나 팀 기능명세서의 백업이 아니다.

## 적용 대상

- 대상: `hyscodebase/chic-harmony-design`의 TanStack Start / Supabase 기반 샌드박스.
- 제외: `kb-intentlock-demo`의 Next.js / Toss 테스트 결제 구현.
- 기준 커밋: `825feb39c9c9c6fcc1db797f9d88179ff529da29`.
- 실제 금융사 연동, 카드 발급, 카드 네트워크 토큰 교환 또는 실결제 성공을 입증하지 않는다.

## 보존할 설계 의도

사용자의 구매 의도에 대한 내부 승인과 외부 결제수단을 분리한다. Intent Token은 이 애플리케이션의 내부 승인 표현이며, 그 자체가 카드 네트워크에서 통용되는 자격증명이라는 뜻은 아니다.

초기 제안은 검증 → 제한된 가상카드 → Mock 네트워크 토큰 → 승인 → 사용 완료/폐기의 흐름을 화면으로 설명하는 것이었다. 각 단계는 서버 측 어댑터 인터페이스로 분리하고, UI는 처리 중 중복 클릭과 실패 상태를 명확히 보여 주도록 했다. 이 구조는 데모의 설명 가능성을 위한 설계이며, 어댑터를 바꾸기만 하면 운영 결제가 안전하게 완성된다는 보장은 아니다.

## 소스에서 확인한 대응

| 항목 | 읽은 소스에서 확인한 것 | 해석 한계 |
|---|---|---|
| 상태 타입 | `kb-payment.types.ts`에 처리 상태와 Intent/Card 상태 union이 존재 | 타입 선언만으로 모든 전이가 실행·검증된 것은 아님 |
| 어댑터 경계 | 검증, 카드 발급, 토큰 교환, 승인, 카드 폐기 메서드가 분리됨 | 실제 금융사 구현이 존재한다는 의미가 아님 |
| 서버 함수 | `kb-payment.functions.ts`에 인증 middleware와 Zod 입력 검증을 거친 POST 함수가 있음 | 인증 middleware 내부와 전체 권한 체계는 이번에 검증하지 않음 |
| Mock 저장소 | `kb-payment.server.ts`가 프로세스/isolate 메모리의 Map을 사용 | 재시작·다중 인스턴스에 걸친 영속성 보장 없음 |
| 반복 요청 | idempotencyKey 응답 캐시와 orderId 기반 승인 결과 재사용이 있음 | 분산 환경의 exactly-once 보장이 아님 |
| 승인 결과 | 성공 경로에서 Intent는 CONSUMED, Card는 DESTROYED로 바꾸어 응답 | 실제 카드 폐기나 금융사 승인 아님 |
| 모드 | 현재 구현은 Mock이며 다른 모드 값에도 Mock으로 fallback | 환경 값만 변경해서 실결제가 활성화되지 않음 |

## 상태 설명 시 주의점

초기 대화에는 Intent의 `ISSUED → VERIFIED → EXCHANGED → AUTHORIZED → CONSUMED`, Card의 `PENDING → ACTIVE → USED → DESTROYED`가 제안되었다. 현재 타입에 이 값들이 있어도 런타임이 모든 중간 상태를 저장하는 것은 아니다.

읽은 Mock 구현은 카드를 생성할 때 ACTIVE로 만들고, 승인 시 Intent를 CONSUMED, Card를 DESTROYED로 직접 변경한다. 따라서 발표에서는 “상태 타입에 포함”과 “실제 실행 경로에서 관찰”을 구별한다. 이번 정리는 소스 읽기만 수행했으며 실행 화면이나 런타임 전이를 관찰하지 않았다.
